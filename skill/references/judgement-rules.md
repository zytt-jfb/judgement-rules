# 判定口径

这套口径是从实战里校正出来的。**每一条都对应过一次误判**，改动前先想清楚为什么当初这么定。

## 一、证件是否与本人一致

### 判定链

```
官方身份证号  vs  业务系统登记的完整身份证号
```

只比对字符串是否相等是错的，必须先分三层：

| 情况 | 判定 | 处置 |
|---|---|---|
| 两者相等 | 一致 | — |
| 系统号**本身不合法** | 系统身份证号有误 | 改系统，证件没问题 |
| 系统号合法、但不等 | 证件非本人 | 查是否借证 |

### 为什么必须先验号

真实案例：系统登记 `110101199002300012`（出生日期 2000-10-62，不存在），官方核验是 `110101199003070029`。
如果只比字符串，会把一个证件完全正常的员工判成"借证"。校验后就清楚了：这是系统录错，不是人的问题。

坏号率在实战里约 **12/21**，即一大半的"不一致"其实是录入错误。不先验号，报告可信度直接崩。

### 验号规则（GB 11643）

1. 长度 18
2. 出生日期 `[6:14]` 必须是真实日期
3. 校验位：加权求和 `[7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]`，模 11，映射 `10X98765432`

`scripts/id_check.py` 已实现。

## 二、姓名一致性

系统里通常有两个姓名字段：**显示名**（可能带区域前缀）和**真实姓名**（可能填错）。

判定顺序：

1. 官方姓名 `==` 显示名 或 `==` 真实姓名 → 姓名对得上
2. 都对不上 → **姓名不符**（证件可能不是本人）
3. 对得上，但两个字段互相矛盾 → 归入**其他发现的问题**

### 区域前缀不算问题

`临邑张三` vs `张三`、`兰山李四` vs `李四`——这是公司为区分重名加的驻地前缀，属命名惯例。长度 ≤4 的前缀一律放行。

### 但要抓真异常

| 现象 | 判定 |
|---|---|
| 真实姓名重复填写（`王五王五`） | 系统人名不规范 |
| 姓名栏填的是公司名（`某某分公司`→赵六） | 系统人名不规范 |
| 形近字错（`钱七`→`孙八`、`周九`→`吴十`） | 系统人名不规范 |
| 显示名含数字编号（`卫五6`） | 系统人名不规范 |
| 前缀超过 4 字 | 系统人名不规范 |

## 三、证类与岗位匹配

| 系统挂的证 | 官方作业类别 | 官方操作项目 |
|---|---|---|
| 低压电工证 | 电工作业 | 低压电工作业 |
| 高压电工证 | 电工作业 | 高压电工作业 |
| 登高证 | 高处作业 | **高处安装、维护、拆除作业** |

**登高证不认「登高架设作业」**——架设是搭脚手架，与安装维护拆除是两个准操项目，不能互相替代。这条是客户明确的口径，默认按严的来。

作业类别就不对 → **证类不符**；类别对但准操项目不对 → **操作项目不符**。

## 四、时效

以官方返回为准，不看系统字段：

- `certStatus != "1"` → **证件状态异常**（实战中 5 = 注销/暂缓）
- `validEndDate < 今天` → **证件已过期**
- `shouldReviewDate < 今天` → **复审逾期**

三者常同时出现，一条记录里都列出来，不要合并成一条。

## 五、"核验不了"不是"有问题"

这是最容易犯的错。三种情况必须分开：

| 情况 | 标签 | 是否算问题 |
|---|---|---|
| 图片空白/分辨率过低/模糊 | 无法识别 | 是（需换证） |
| 图片清晰但二维码读不出 | 未取得核验 | 否（我方手段受限） |
| 附件没下载/系统没上传 | 未核验 | 否 |

### 怎么区分前两种

量图片质量，任一条命中即判"无法识别"：

- 文件 < 80 KB（疑似空白或截图）
- 长边 < 900 px
- 边缘锐度（FIND_EDGES 后方差）< 600
- 灰度标准差 < 25

反例警戒：实战中一批被判"读不出"的证件，图片平均 **11.6 MB / 3737 px / 锐度 2427**——又大又清楚，纯属解码器能力不足。把这些标成"无法识别"，等于把工具缺陷赖到员工头上，客户一对人工结果就会发现 41 人全被冤枉。

## 六、一证多人

独立的两条证据链，互相印证：

1. **文件层面**：多人引用同一 `absPath`，或下载后图片 MD5 相同
2. **官方层面**：同一官方身份证号 / 同一档案编号出现在多个系统账号下

两条都命中 → 冒用无疑。实战中抓到过一张证被 4 人挂、另一张被 3 人挂。

注意排除正常共享：公司级保险单、团体险条款本来就是全员共用，只对证件类文件做此项检查。

## 七、先证明数据没串，再谈判定

任何比对结论的前提是"这份文件确实属于这个人"。数据串位的破坏力远大于判定规则写错——它会把无辜的人判成借证，而且看起来毫无破绽。

### 必查的三项

1. **同一人的多个证件类型是否指向同一 fileId** → 是则面板未刷新
2. **同一 fileId 是否出现在多个不同人名下** → 是则至少有一方被串位
3. **文件名里是否出现别人的姓名** → 最直接的铁证（如"张三-低压电工证.jpg"出现在冯二名下）

第 3 项有子串误报：`陈三` 含 `刘景`、`褚四` 含 `高峰`。判定时要排除"该姓名是本人姓名的子串"这种情况。

### 实战规模

- 658 人中 **114 人（17%）** 被串位，集中在 5 个连续区块，最大一块 86 人
- 串位同时污染了"非本人"判定和"读不出二维码"统计——83 个"读不出"里有 72 个其实是读错了文件
- 修正后："证件非本人"从 9 人降到 **2 人**

### 处理原则

一旦确认串位，**该人的全部结论作废**，标记为"需重核"，不要试图部分保留。宁可留白，也不要把错的结论交给客户。

## 八、与人工结果冲突时

不要一发现不一致就改规则。先归类：

| 类型 | 特征 | 处理 |
|---|---|---|
| 叫法差异 | 人工"重复证件" vs 我方"证类不符" | 不改，加映射说明即可 |
| 我方判定错 | 人工有证据证明正常，我方判有问题 | 改规则 |
| 对方漏项 | 我方有权威数据支撑 | 保留结论，标注"人工未记录" |
| 数据缺失 | 人工手上有脱敏数据、结构上看不到 | 保留，说明差异根源 |

改规则前必须先确认属于哪一类，否则会越改越松。
